# RenderDoc 使用指南：先抓一帧，再查画面

## 1. 它到底是干什么的？

RenderDoc 可以把程序画出某一帧时用到的绘制命令、纹理、模型数据和 Shader（着色器）记录下来。你可以慢慢检查：这个物体是谁画的？用了哪张贴图？为什么某个像素变成了黑色？

它不是录屏，也不是完整的游戏工程备份。`.rdc` 抓帧文件不能还原整个游戏源码。它主要用来查 GPU 渲染问题；CPU 逻辑、网络卡顿、完整性能分析通常还需要其他工具。

这份说明面向 Windows 上自己的图形程序，以及允许你调试的程序。常见 API 有 D3D11、D3D12、Vulkan、OpenGL；并不是任何应用、任何扩展都能抓。不要向带反作弊或禁止注入的程序强行注入，也不要为了抓帧关闭系统安全保护。

## 2. 从哪里启动？

本次构建的启动位置和验证结果见 [编译说明.md](D:/Tools/renderdoc/docs-zh/编译说明.md)。正常的 x64 Release 界面程序是 `D:/Tools/renderdoc/x64/Release/qrenderdoc.exe`。

请保留输出文件夹里的 DLL、插件和其他配套文件。不要只把一个 EXE 拿走，也不要混用正式安装版和自己编译版的 DLL。

优先使用 64 位 RenderDoc 抓 64 位程序。抓 32 位程序可能还需要配套的 32 位捕获组件；只编译 x64 不等于已经准备好所有 32 位组件。

## 3. 第一次抓帧，照着做

1. 打开 RenderDoc，选择 `File → Launch Application`，也就是“启动一个要抓帧的程序”。
2. 在 `Executable` 选择真正负责渲染的 EXE，不是快捷方式。第一次练习，优先选你自己的小 Demo，不要选复杂启动器。
3. 在 `Working Directory` 填程序平时运行时的工作目录。留空默认用 EXE 所在目录；如果贴图、配置文件通过相对路径加载，目录填错就容易启动失败。
4. 在 `Command-line Arguments` 填必要的启动参数。不需要参数就留空，其他捕获选项先保持默认。
5. 点击 `Launch`。程序启动后，切换到它的窗口，等想检查的画面稳定出现。通常能看到 RenderDoc 的叠加提示，表示已经接入。
6. 按 `F12` 或 `Print Screen`。这不是截图快捷键，而是请求记录接下来的一帧。抓帧时短暂卡一下通常正常。
7. 回到 RenderDoc 的捕获连接窗口，双击抓帧缩略图打开。也可以在程序退出后查看捕获结果，不必为了打开抓帧立即关闭程序。
8. 使用 `File` 菜单里的保存功能，把这帧保存成 `.rdc`。临时捕获不要当成已经长期保存。

成功的标准：能打开 `.rdc`，看到事件列表和纹理，并且切换绘制事件时能检查对应状态。仅仅看到目标程序启动不算抓帧成功。

按键被程序或输入法占用时，试试捕获连接窗口里的抓帧按钮；有需要也可以使用延时或指定帧捕获。多窗口程序要确认抓的是实际渲染窗口。

注意：启动面板中的 `Save Settings` 保存的是启动配置 `.cap`，不是画面记录 `.rdc`。

## 4. 面对一堆窗口，先看这几个

| 窗口 | 用人话说 | 什么时候看 |
| --- | --- | --- |
| Event Browser | 这一帧的“绘制步骤清单” | 找是哪次 Draw 或 Dispatch 出了问题 |
| Texture Viewer | 看贴图和画到纹理里的结果 | 看颜色、深度、输入贴图、输出画面 |
| Pipeline State | 选中那一步时，GPU 的“配置清单” | 看 Shader、资源绑定、深度、混合等状态 |
| Mesh Viewer | 看模型顶点和变换后的形状 | 查模型错位、飞走、拉长、UV 错误 |
| API Inspector | 更细的图形 API 调用和参数 | 核对某次调用实际传了什么 |

`EID` 是事件编号，不是耗时。默认事件列表主要显示 Draw、Dispatch、Clear、Copy 等动作，不是所有 API 调用。选中事件后，其他窗口会跟着切换；不要拿上一事件的状态解释下一事件的问题。

`Draw` 是画几何体，`Dispatch` 是运行计算着色器，`Clear` 是清空，`Copy` 是复制。`Render Target` 可以理解成“这一步把画面写到哪里”。`Pass` 通常指一组有共同目的的渲染步骤，比如阴影、透明物体、后处理。

## 5. 怎样找到“这个物体是谁画的”？

1. 在 Texture Viewer 找到最终画面。不是每个事件的第一个输出纹理都是最终画面，必要时查看输出列表或帧末的相关事件。
2. 在 Event Browser 从后往前或分段检查，观察画面什么时候发生变化。如果程序有阴影、主场景、后处理等标记，先按这些分组缩小范围。
3. 找到可疑 Draw 后，在 Pipeline State 核对它的输出目标、输入贴图、Shader 和常量。
4. 如果画的是模型，再去 Mesh Viewer 检查顶点输入和顶点 Shader 输出；如果是计算步骤，就看 Compute 阶段的资源和线程组配置。

纹理窗口可能在“跟随某个绑定槽”，也可能在“锁定一张纹理”。双击纹理打开锁定标签后，切事件会继续看同一资源。查某张纹理如何变化时很有用，但不要误以为它始终是当前 Draw 的输出。

## 6. 常见问题，按这个顺序查

### 物体没画出来

先确认有没有对应 Draw，再确认写到了正确的 Render Target。接着查 Viewport（视口）和 Scissor（裁剪区域），看看是不是画到屏幕外或被裁掉了。

然后看 Mesh Viewer：输入顶点对不对？顶点 Shader 输出是不是飞出去了？最后查背面剔除、深度/模板测试、透明度和颜色写入开关。物体不见了，不一定是 Shader 没执行。

### 贴图不对、颜色不对、画面黑了

先看实际绑定的贴图，再查 mip（不同分辨率层级）、数组层、采样器和 UV。不要只看资源名字；同名资源也可能不是同一张。

再查常量和 Shader 输出，最后检查混合和颜色空间。HDR、深度纹理、法线纹理不一定能用普通 RGB 显示直接看懂。Texture Viewer 中可以切换通道、调整显示范围；显示成黑色不等于数据全是零。

### 某个像素为什么是这个颜色？

在 Texture Viewer 右键选中问题像素，然后用 `Pixel History`（像素历史）检查哪些绘制修改或尝试修改了它、是否被深度等测试挡住。找到目标 Draw 后，再尝试 `Debug Pixel`。

像素历史和 Shader 调试都受 API、格式、Shader 特性等限制。按钮灰了不一定是操作错误。当前仓库文档说明 Shader 调试支持 D3D11、D3D12、Vulkan，但并不支持所有 Shader；OpenGL 不能照搬这套单步调试流程。

## 7. Shader 怎么看、怎么改？

在 Pipeline State 找到对应阶段的 Shader，点击查看按钮。顶点着色器通常叫 VS，像素/片元着色器叫 PS/FS，计算着色器叫 CS。

想按源代码单步调试，需要目标程序编译 Shader 时保留相应调试信息；这和“把 RenderDoc 自己编译成 Debug”不是一回事。没有源代码时可能只有反汇编；保留信息也不保证每种指令都能调试。

顶点调试从 Mesh Viewer 的顶点输入表选择顶点并右键开始；像素调试从 Texture Viewer 选择像素开始；计算调试在 Compute 阶段指定线程组和组内线程。

想快速验证一个猜测，可以用 Shader 旁的编辑按钮，修改后按 `F5` 或 `Apply changes` 应用。它改变的是当前抓帧的回放，可能影响这帧中所有使用该 Shader 的动作，不只影响当前选中的 Draw。

关闭编辑窗口会撤销这种场景 Shader 替换。它不会自动修改你的游戏工程源码，确认有效后仍需要把改动写回自己的工程并重新运行。没有可用源代码或编译工具时，编辑也可能不可用。

## 8. 抓不到帧时，不要乱开选项

| 现象 | 优先检查 |
| --- | --- |
| 程序无法启动、找不到贴图 | EXE、工作目录、参数是否和正常启动一致 |
| 启动器有连接，游戏没有 | 优先直接启动真正渲染的 EXE；必要时启用 `Capture Child Processes` 并连接对应子进程 |
| 已运行的程序注入后抓不到 | 图形 API 可能已经初始化；重新从 RenderDoc 启动更可靠 |
| 快捷键没反应 | 目标窗口焦点、快捷键冲突、连接窗口的抓帧按钮 |
| 文件打不开或回放失败 | RenderDoc 版本、API 支持、显卡/驱动能力以及日志 |
| 抓帧很大、抓帧很慢 | 先少抓几帧；不要无目的开启记录调用栈或引用全部资源 |
| 只剩英文界面，看不懂 | 用上面的窗口对照表；本说明是中文手册，不是界面汉化补丁 |

`Inject into Process` 不是“任何运行中的程序都能随时接管”。它要求足够早、尚未初始化相关图形 API；太晚注入可能失败甚至崩溃。

不要把全局 Hook、管理员权限或关闭安全功能作为默认解决办法。尤其不建议新手使用全局 Hook，它会影响其他进程。

## 9. 分享给同事时带什么？

发 `.rdc`，并写明 API、RenderDoc 版本、显卡/驱动、问题 EID、像素坐标和预期画面。可以附截图，但只发截图无法让别人查看完整状态。

抓帧中可能含内部纹理、Shader 和业务数据，分享前确认权限。为了减少兼容性问题，优先用同一版本打开，最好同时提供对应构建版本；不能保证不同机器回放百分之百一致。

## 10. 最短记忆版

从 RenderDoc 启动程序 → 到问题画面按 F12 → 打开并保存 `.rdc` → 在事件列表找相关 Draw → 查纹理、模型和 Pipeline State → 必要时查像素历史或调试 Shader → 回自己的源码修复 → 重新抓帧验证。
